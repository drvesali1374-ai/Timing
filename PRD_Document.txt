# راهنمای استفاده از سند

این سند حاصل پنج دور تصمیم‌گیری با مالک محصول است و باید به‌عنوان مرجع اصلی پروژه استفاده شود. سند سه نوع گزاره دارد:

- **تصمیم قطعی محصول:** انتخابی که مالک محصول صریحاً اعلام کرده است؛ ایجنت حق تغییر آن را بدون تأیید ندارد.
- **تصمیم/پیشنهاد فنی:** راهکار معماری برای تحقق تصمیم قطعی؛ ایجنت باید آن را بررسی کند و هر تغییر ضروری را با دلیل و اثر آن مستند سازد.
- **قید مهندسی و شفافیت:** محدودیتی که برای جلوگیری از محاسبه نادرست، گزارش گمراه‌کننده یا تخریب داده لازم است.

این سند تضمین نمی‌کند که یک نرم‌افزار بدون آزمون و بازبینی «بی‌خطا» خواهد بود. هیچ دستور متنی به‌تنهایی نمی‌تواند خطا را ناممکن کند. به همین دلیل، توسعه باید مرحله‌ای، مبتنی بر آزمون‌های قابل تکرار، معیارهای پذیرش و شواهد اجرایی باشد. ادعای تکمیل بدون آزمون قابل مشاهده پذیرفته نیست.

**اصل مهم:** تمام قابلیت‌های انتخاب‌شده در محدوده نسخه اول هستند. تقسیم کار به فازهای توسعه فقط برای کنترل کیفیت و کاهش ریسک است؛ بهانه‌ای برای حذف قابلیت‌ها یا موکول‌کردن آن‌ها به نسخه‌ای نامعلوم نیست.

# بخش ۱ ـ خلاصه اجرایی و منشور محصول

## ۱.۱. مأموریت محصول

ساخت یک وب‌اپلیکیشن حرفه‌ای برای انجام مطالعات زمان‌سنجی خطوط تولید صنعتی که کارشناس بتواند از تعریف پروژه و ساختار خط تا ثبت مشاهدات، ارزیابی عملکرد، محاسبه زمان نرمال و استاندارد، ترسیم نمودارهای OPC/FPC، مقایسه اپراتورها و تهیه گزارش را در یک محیط یکپارچه انجام دهد.

محصول باید در عین برخورداری از منطق مهندسی دقیق، برای کاربر آماتور نیز قابل فهم باشد. کاربر نباید برای یافتن اقدام بعدی، تشخیص محل ورود داده یا فهم خطا مجبور به حدس‌زدن شود.

## ۱.۲. معیارهای اصلی موفقیت

۱. سادگی و جلوگیری از سردرگمی.  
۲. سرعت انجام کار و کاهش کلیک و ورود اطلاعات تکراری.  
۳. صحت محاسبات مهندسی و نمایش شفاف فرض‌ها.  
۴. زیبایی، نشاط و تعامل خوشایند بدون شلوغی و اغراق.  
۵. انعطاف‌پذیری تنظیمات در بخش پیشرفته.  
۶. حفظ داده‌ها، پشتیبان‌گیری و امکان بازیابی.  
۷. استقلال کامل از اینترنت عمومی در زمان بهره‌برداری.

## ۱.۳. محدوده قطعی نسخه اول

نسخه اول باید تمام موارد زیر را پوشش دهد:

- مدیریت پروژه‌ها؛ هر پروژه فقط یک خط تولید و یک محصول.
- ساختار خط تولید ← ایستگاه ← فعالیت ← عنصر کاری ← مشاهده.
- تعریف و مرتب‌سازی ایستگاه‌ها و فعالیت‌ها با Drag & Drop.
- گروه‌های دلخواه فعالیت برای تخصیص مجازها.
- ثبت چند اپراتور و برگه مستقل هر اپراتور برای هر فعالیت.
- ثبت زمان دستی و Paste چندسلولی از Excel؛ بدون کرنومتر داخلی.
- پشتیبانی از روش برگشت به صفر و روش پیوسته کرنومتر.
- ثبت بازه‌های هم‌پوشان برای کار هم‌زمان اپراتور و ماشین.
- جدول چرخه‌محور با هر چرخه در یک ردیف و هر عنصر کاری در یک ستون.
- Undo/Redo، اعتبارسنجی، وضعیت مشاهدات و هشدار داده‌های غیرعادی.
- ارزیابی وستینگهاوس در سطح عنصر کاری و قابل استفاده برای همه مشاهدات همان عنصر.
- تعریف دسته‌های مجاز در سطح گروه و امکان بازنویسی در سطح فعالیت.
- هر دو روش محاسبه مجازها و زمان استاندارد.
- تحلیل آماری و مقایسه اپراتورها.
- ساخت خودکار و ویرایش OPC/FPC.
- داشبورد قابل شخصی‌سازی.
- خروجی Excel و PDF، خروجی سریع و مرکز جامع گزارش‌ها.
- تنظیمات پیشرفته، فارسی/RTL، تقویم و ارقام قابل انتخاب، تم روشن/تیره.
- ذخیره خودکار، پشتیبان‌گیری خودکار و دستی، بازیابی و بسته خروجی کامل پروژه.
- کپی پروژه با انتخاب بخش‌های قابل کپی.
- حذف دائمی اطلاعات وابسته پس از تأیید صریح.
- تاریخچه تغییرات مهم و محاسبه مجدد پس از تغییرات مؤثر.
- طراحی واکنش‌گرا برای کامپیوتر، تبلت و موبایل.

## ۱.۴. موارد خارج از محدوده نسخه اول

موارد زیر بدون تصمیم جدید مالک محصول وارد نسخه اول نشوند:

- حساب کاربری، ورود با رمز عبور و مدیریت نقش‌های چندکاربره.
- کرنومتر داخلی و ثبت خودکار لحظه‌ای از سخت‌افزار.
- اتصال مستقیم به PLC، MES، ERP یا تجهیزات صنعتی.
- وابستگی به API، فونت، تصویر، CDN، نقشه یا سرویس ابری خارجی.
- تشخیص خودکار فعالیت از دوربین یا هوش مصنوعی آنلاین.
- برنامه‌ریزی پیشرفته تولید و زمان‌بندی کل کارخانه.
- حذف/تغییر روش‌های مهندسی با الگوریتم‌های مبهم یا خودکار.

# بخش ۲ ـ کاربران، محیط و محدودیت‌های عملیاتی

## ۲.۱. کاربر اصلی

یک کارشناس یا کاربر شخصی مسئول انجام مطالعه زمان‌سنجی. نرم‌افزار برای نسخه اول چندکاربره نیست و صفحه ورود نام کاربری/رمز عبور ندارد.

## ۲.۲. محیط اجرا

- برنامه روی کامپیوتر یا سرور داخلی شرکت اجرا می‌شود.
- کارکرد عملیاتی نباید به اینترنت عمومی نیاز داشته باشد.
- مرورگر از طریق شبکه داخلی به سرور برنامه متصل می‌شود.
- Backend و فایل پایگاه داده باید روی همان میزبان اجرا/ذخیره شوند؛ فایل SQLite نباید مستقیماً روی پوشه اشتراکی شبکه یا NAS باز شود.
- دسترسی شبکه باید با Firewall و محدودسازی آدرس/زیرشبکه به دستگاه‌های مجاز محدود شود؛ نبود صفحه ورود به معنی بازبودن برنامه برای تمام شبکه نیست.
- تمام فونت‌ها، آیکون‌ها، نمودارها، کتابخانه‌ها و فایل‌های لازم در زمان اجرا باید محلی و بسته‌بندی‌شده باشند.
- هیچ درخواست زمان اجرا به دامنه اینترنتی خارجی ارسال نشود؛ Telemetry و Analytics خارجی غیرفعال باشند.

## ۲.۳. شناسایی تغییرات بدون حساب کاربری

از آنجا که ورود کاربر وجود ندارد، سیستم نباید نام شخص واقعی را جعل کند. در تاریخچه تغییرات، عامل تغییر با مقدار «کاربر محلی» یا شناسه نصب/میزبان ثبت شود. اگر در آینده تشخیص افراد مختلف لازم شد، آن قابلیت نیازمند تصمیم و احراز هویت جداگانه است.

## ۲.۴. راهبرد استقرار

دو حالت استقرار مجاز است:

۱. **تک‌سیستمی:** برنامه و داده روی یک کامپیوتر اجرا شوند و همان دستگاه مرورگر را باز کند.  
۲. **سرور داخلی:** برنامه و پایگاه داده روی یک سرور فیزیکی/مجازی داخلی نصب شوند و مرورگر مجاز از طریق شبکه داخلی به API آن وصل شود.

در هر دو حالت، موتور پایگاه داده و فایل آن روی میزبان Backend قرار می‌گیرند، نه روی درایو شبکه کلاینت.

# بخش ۳ ـ واژه‌نامه دامنه و قواعد مفهومی

| اصطلاح | تعریف مورد استفاده در نرم‌افزار |
|---|---|
| پروژه | یک مطالعه روی یک خط تولید و یک محصول مشخص |
| خط تولید | محدوده اصلی جریان تولید در پروژه |
| ایستگاه | بخش/موقعیت کاری در خط تولید |
| فعالیت | کار یا فرایند مشخص در یک ایستگاه که برای آن برگه زمان‌سنجی ساخته می‌شود |
| عنصر کاری | جزء قابل تشخیص و اندازه‌گیری از یک فعالیت |
| چرخه | یک بار اجرای کامل فعالیت؛ یک ردیف در جدول زمان‌سنجی |
| مشاهده | مقدار ثبت‌شده مربوط به یک عنصر کاری در یک چرخه |
| جلسه زمان‌سنجی | مجموعه چرخه‌های یک فعالیت برای یک اپراتور با روش اندازه‌گیری مشخص |
| زمان مشاهده‌شده | زمان خام ثبت‌شده و معتبر برای محاسبه |
| ضریب عملکرد | ضریب حاصل از ارزیابی وستینگهاوس |
| زمان نرمال | زمان مشاهده‌شده تعدیل‌شده با ضریب عملکرد |
| مجاز | درصد یا سهم زمانی مجاز که طبق مبنای انتخابی به زمان نرمال اعمال می‌شود |
| زمان استاندارد | زمان نرمال پس از اعمال مجاز با فرمول انتخاب‌شده |
| مشاهده مشکوک | داده‌ای که یک قاعده آماری آن را برای بازبینی علامت‌گذاری کرده است؛ حذف خودکار نمی‌شود |
| گره نمودار | رویداد یا فعالیت نمایش‌داده‌شده در OPC/FPC |

**تمایز ضروری:** نوع فعالیت برای نماد نمودار فرایند و نوع عنصر کاری برای تحلیل زمان دو مفهوم مستقل هستند. برای مثال، فعالیت می‌تواند از نوع «عملیات» باشد، در حالی که عناصر آن شامل کار دستی و زمان خودکار ماشین باشند.

# بخش ۴ ـ نیازمندی‌های عملکردی محصول (Functional Requirements)

## FR-01 ـ مدیریت پروژه

- صفحه اصلی پس از ورود، پروژه‌ها را به صورت کارت نمایش دهد.
- هر کارت شامل نام پروژه، خط تولید، محصول، تاریخ مطالعه، وضعیت و میزان پیشرفت باشد.
- ایجاد پروژه حداقل به نام پروژه، نام خط تولید، نام محصول و تاریخ مطالعه نیاز داشته باشد؛ سایر مشخصات اختیاری‌اند.
- جست‌وجو، مرتب‌سازی و بازکردن پروژه از صفحه اصلی فراهم باشد.
- هر پروژه تنظیمات و داده مستقل داشته باشد.
- کاربر بتواند پروژه قبلی را با انتخاب بخش‌های موردنظر به‌عنوان پروژه جدید کپی کند.
- کپی عادی نباید مشاهدات خام، نتایج محاسبه‌شده یا تاریخچه پروژه مبدأ را به پروژه جدید منتقل کند، مگر کاربر صریحاً این بخش را انتخاب کند؛ پیش‌فرض فقط ساختار و تنظیمات است.

## FR-02 ـ ساختار تولید

- هر پروژه یک خط تولید و یک محصول دارد.
- ساختار داده خط ← ایستگاه ← فعالیت ← عنصر کاری ← مشاهده باشد.
- ایستگاه‌ها و فعالیت‌ها با Drag & Drop مرتب شوند.
- نمایش ساختار درختی باشد؛ انتخاب هر گره، محتوای مرتبط را در فضای اصلی نشان دهد.
- هر فعالیت دارای نام، شرح اختیاری، ترتیب، گروه مجازها و نوع رویداد فرایندی است.
- نوع فعالیت حداقل شامل عملیات، بازرسی، حمل‌ونقل، تأخیر و انبارش باشد.
- برای عناصر کاری، نام و شرح ثبت شود؛ سایر مشخصات اختیاری باشند.
- نوع عنصر کاری حداقل شامل دستی، خودکار ماشین، انتظار و هم‌زمان/دارای هم‌پوشانی باشد.
- عنصر کاری دارای شناسه پایدار باشد؛ تغییر نام نباید ارتباط تاریخی و گره‌های نموداری را از بین ببرد.

## FR-03 ـ صفحه اختصاصی فعالیت

صفحه هر فعالیت دارای زبانه‌های زیر باشد:

۱. مشخصات  
۲. عناصر کاری  
۳. زمان‌سنجی  
۴. تحلیل نتایج

صفحه باید اطلاعات مهم، وضعیت تکمیل و اقدام بعدی را نشان دهد. فرم‌ها و زبانه‌ها باید در دسکتاپ و موبایل قابل استفاده باشند.

## FR-04 ـ گروه فعالیت و مجازها

- کاربر گروه‌های دلخواه مانند «کار دستی»، «کار ماشینی» یا گروه‌های اختصاصی خود ایجاد کند.
- هر فعالیت بتواند به یک گروه مجازها تخصیص یابد.
- مجازها در سطح گروه به‌صورت دسته‌های مجزا نگهداری شوند.
- فعالیت مقادیر گروه را به ارث ببرد.
- کاربر بتواند در سطح فعالیت هر دسته را بازنویسی کند.
- رابط کاربری منبع هر مقدار را مشخص کند: «ارث‌رسیده از گروه» یا «اختصاصی فعالیت».
- مجموع درصدهای مجاز برای محاسبه از روی دسته‌های فعال و مقدار نهایی آن‌ها ساخته شود.
- روش اعمال مجاز در سطح پروژه انتخاب شود: درصد نسبت به زمان نرمال یا سهم از زمان استاندارد.

## FR-05 ـ اپراتورها

- چند اپراتور در یک پروژه ثبت شوند.
- هر اپراتور شناسه و نام نمایشی داشته باشد؛ شناسه/نام می‌تواند کد داخلی باشد.
- برای هر فعالیت، برگه‌های زمان‌سنجی اپراتورها جدا باشند.
- در صفحه فعالیت، جلسه‌ها و نتایج اپراتورها قابل مشاهده و مقایسه باشند.
- اپراتور در سطح پروژه تعریف شود و بتواند در چند فعالیت همان پروژه شرکت کند.

## FR-06 ـ جلسه زمان‌سنجی و انتخاب روش

- برای هر ترکیب فعالیت و اپراتور، یک یا چند جلسه زمان‌سنجی وجود داشته باشد.
- هنگام ایجاد جلسه، روش اندازه‌گیری انتخاب شود: برگشت به صفر یا پیوسته.
- واحد پایه ذخیره‌سازی زمان ثانیه باشد.
- تاریخ و زمان جلسه، اپراتور، فعالیت، روش، توضیح اختیاری و وضعیت جلسه نگهداری شوند.
- کرنومتر داخلی در نسخه اول ساخته نشود.
- جلسه جدید مستقل از جلسه قبلی باشد؛ مبنای قرائت پیوسته با شروع جلسه جدید از نو آغاز شود.

## FR-07 ـ جدول ثبت زمان

## FR-08 ـ روش برگشت به صفر

## FR-09 ـ روش پیوسته

- در روش پیوسته، کاربر قرائت تجمعی کرنومتر را در نقطه پایان هر عنصر ثبت می‌کند.

- مقدار قرائت تجمعی خام و مقدار تفاضلی محاسبه‌شده هر دو ذخیره شوند.
- قرائت تجمعی در یک خط زمانی نباید به عقب برگردد؛ مقدار کمتر از قرائت قبلی خطا است، مگر در رخداد جداگانه «ریست/شروع جلسه جدید» که باید جلسه جدید ایجاد شود.

- برای یک عنصر که در چند چرخه تکرار می‌شود، اتصال انتهای چرخه قبلی به ابتدای چرخه بعد باید در داده خام قابل ردیابی باشد.

## FR-10 ـ کار هم‌زمان اپراتور و ماشین

- مدت عنصر برابر پایان منهای شروع باشد.

- مجموع زمان کار دستی، زمان خودکار ماشین و زمان انتظار به‌صورت شاخص‌های مجزا گزارش شوند.
- روش پیوسته تک‌خطی برای کارهای ترتیبی مناسب است؛ ثبت هم‌زمانی باید از طریق بازه‌های زمانی/خطوط زمانی مستقل انجام شود. سیستم نباید با تبدیل صوری یک توالی پیوسته، هم‌زمانی جعلی بسازد.
- اگر اطلاعات کافی برای تعیین مبدأ مشترک/بازه هم‌پوشانی وارد نشده باشد، زمان چرخه به‌عنوان «محاسبه‌نشده/نیازمند تکمیل» نشان داده شود.

## FR-11 ـ کنترل کیفیت مشاهدات

## FR-12 ـ تعداد نمونه

- تعداد نمونه هدف توسط کاربر برای کل فعالیت تعیین شود، نه جداگانه برای هر اپراتور.

- تعداد مشاهدات معتبر هر عنصر و هر اپراتور جداگانه نمایش داده شود.
- اگر تعداد نمونه به هدف نرسیده باشد، هشدار واضح داده شود.
- کاربر بتواند با درج دلیل، مطالعه را نهایی کند.
- رسیدن به هدف کاربر فقط به معنای «رسیدن به تعداد هدف ثبت‌شده» است و نباید به‌طور خودکار «کفایت آماری تضمین‌شده» تلقی شود.
- شاخص‌های پراکندگی و عدم‌قطعیت برای تصمیم آگاهانه نمایش داده شوند.

## FR-13 ـ ارزیابی وستینگهاوس

- یک ارزیابی برای هر عنصر کاری ثبت شود.
- ارزیابی عنصر به تمام مشاهدات همان عنصر، از تمام اپراتورهای آن فعالیت، اعمال شود؛ این رفتار مطابق تصمیم کاربر است.
- ارزیابی شامل مهارت، تلاش، شرایط و یکنواختی است.
- ضریب عملکرد: `R = 1 + Skill + Effort + Conditions + Consistency`.
- جدول مرجع باید قابل مشاهده و قابل ویرایش در تنظیمات پیشرفته باشد.
- هر جدول مرجع نام، نسخه، تاریخ/منبع و توضیح داشته باشد.
- برای Seed اولیه، یک نسخه رایج و قابل بازبینی از جدول کلاسیک Westinghouse با مقادیر زیر بارگذاری شود. این جدول فقط نقطه شروع نرم‌افزار است و پیش از استفاده عملی باید توسط کارشناس/رویه شرکت تأیید شود؛ آن را استاندارد جهان‌شمول معرفی نکن.

| عامل | درجه | مقدار |

| مهارت | A1 / A2 | +0.15 / +0.13 |
| مهارت | B1 / B2 | +0.11 / +0.08 |

- کاربر باید بتواند مقادیر، عنوان درجه‌ها و متن راهنمای فارسی را ویرایش کند و جدول سفارشی را با نسخه جدید ذخیره کند؛ تغییر جدول نباید محاسبات تاریخی را بی‌صدا تغییر دهد.
- امکان کپی ارزیابی برای عنصر مشابه وجود داشته باشد.
- در مقایسه اپراتورها، چون امتیاز در سطح عنصر مشترک است، ضریب وستینگهاوس برای همان عنصر در اپراتورها مشترک نمایش داده شود؛ سیستم نباید بدون تصمیم جدید، ارزیابی جداگانه اپراتوری جعل کند.

## FR-14 ـ محاسبه زمان مشاهده‌شده و زمان نرمال

برای عنصر کاری `e` و مشاهدات معتبر آن:

`OT_e = mean(valid observed durations for element e)`

`NT_e = OT_e × R_e`

- مشاهدات خارج‌شده از محاسبه در OT وارد نمی‌شوند.
- `R_e` از ارزیابی وستینگهاوس همان عنصر به دست می‌آید.
- میانگین اپراتور و میانگین تجمیعی عنصر به‌صورت جداگانه قابل مشاهده باشند.
- روش تجمیع پیش‌فرض فعالیت، میانگین وزنی بر اساس تعداد مشاهدات معتبر است؛ یعنی همه مشاهدات معتبر وزن یکسان دارند. میانگین‌های اپراتوری نیز جداگانه نمایش داده شوند.
- این قاعده تجمیع باید در گزارش و تنظیمات پیشرفته آشکار باشد؛ اگر کارشناس میانگین اپراتورها با وزن برابر را انتخاب کند، آن انتخاب نیز باید ثبت شود.

## FR-15 ـ مجازها و زمان استاندارد

در پروژه یکی از دو مبنای زیر انتخاب می‌شود:

**الف) مجاز به‌صورت درصدی از زمان نرمال:**

`A = sum(allowance category percentages)`

`ST = NT × (1 + A)`

**ب) مجاز به‌صورت سهمی از زمان استاندارد:**

`A = sum(allowance category percentages)`

`ST = NT / (1 - A)`

- درصدها به‌صورت مقدار اعشاری محاسباتی ذخیره شوند؛ مثلاً ۱۵٪ برابر `0.15`.
- دسته‌های مجاز در گروه فعالیت تعریف می‌شوند و فعالیت می‌تواند مقادیر هر دسته را بازنویسی کند.
- در گزارش، مقدار هر دسته، مجموع مجاز، روش انتخابی و فرمول صریح نمایش داده شود.
- در روش دوم، مجموع `A` باید کمتر از ۱۰۰٪ باشد؛ در غیر این صورت محاسبه ممنوع و خطای قابل فهم نمایش داده شود.
- نرخ ۱۵٪ یا هر عدد نمونه صرفاً مثال است؛ مقدار پیش‌فرض نباید به‌عنوان نرخ جهانی یا نرخ مصوب شرکت معرفی شود.

## FR-16 ـ محدودیت مهم زمان استاندارد در فعالیت‌های هم‌پوشان

زمان عناصر و زمان سپری‌شده چرخه در کار هم‌زمان دو مفهوم متفاوت‌اند. جمع زمان استاندارد تک‌تک عناصر، زمان استاندارد کل چرخه را به دست نمی‌دهد، زیرا عناصر می‌توانند هم‌پوشانی داشته باشند.

بنابراین:

- زمان مشاهده‌شده هر عنصر، زمان نرمال هر عنصر و زمان استاندارد هر عنصر قابل محاسبه است.
- زمان سپری‌شده واقعی چرخه از بازه‌های شروع/پایان محاسبه می‌شود.
- برای فعالیت کاملاً ترتیبی، زمان استاندارد فعالیت می‌تواند از جمع زمان استاندارد عناصر تشکیل شود.
- برای فعالیت دارای هم‌پوشانی، سیستم نباید زمان استاندارد کل فعالیت را با جمع ساده عناصر محاسبه کند.
- تا زمانی که مدل زمان‌بندی/تقدم‌وتأخر و قاعده مهندسی مورد تأیید برای تبدیل زمان عناصر به زمان استاندارد چرخه تعریف نشده، خروجی زمان استاندارد کل فعالیت باید «نیازمند قاعده تجمیع/بازبینی مهندسی» نشان داده شود؛ در عوض زمان‌های استاندارد عناصر و زمان سپری‌شده مشاهده‌شده چرخه نمایش داده شوند.
- ایجنت مجاز نیست برای رفع این محدودیت فرمول دلخواه و فاقد مستند بسازد.

## FR-17 ـ تحلیل آماری

شاخص‌های قابل محاسبه حداقل شامل موارد زیر باشند:

- تعداد کل، معتبر، مشکوک و خارج‌شده از محاسبه
- میانگین، میانه، حداقل، حداکثر و دامنه
- انحراف معیار نمونه
- واریانس نمونه
- ضریب تغییرات (CV)
- چارک‌ها و دامنه بین‌چارکی (IQR)
- نمودار توزیع/هیستوگرام
- نمودار روند مشاهدات به ترتیب چرخه
- بازه اطمینان میانگین، در صورت تحقق پیش‌فرض‌های لازم و نمایش روش/سطح اطمینان
- پیشرفت نسبت به تعداد نمونه هدف

فرمول‌های پایه:

`mean = sum(x_i) / n`

`sample variance = sum((x_i - mean)^2) / (n - 1)` برای `n > 1`

`sample SD = sqrt(sample variance)`

`CV% = (sample SD / mean) × 100`، مشروط به میانگین غیرصفر.

در صورت `n < 2`، SD و واریانس باید «قابل محاسبه نیست» باشند، نه صفر.

## FR-18 ـ تشخیص مشاهدات غیرعادی

- روش اولیه پیشنهادی: امتیاز Z تعدیل‌شده بر پایه Median و MAD.
- فرمول: `M_i = 0.6745 × (x_i - median(x)) / MAD`.
- مقدار `|M_i| > 3.5` به‌عنوان معیار پیش‌فرض علامت‌گذاری اولیه، نه حذف قطعی، استفاده شود.
- آستانه و روش در تنظیمات پیشرفته قابل مشاهده/تغییر باشد.
- اگر MAD صفر باشد یا نمونه بسیار کم باشد، روش باید به‌صورت کنترل‌شده به IQR یا هشدار «داده ناکافی برای تشخیص آماری مطمئن» برود؛ تقسیم بر صفر یا هشدار جعلی ممنوع است.
- پیام هشدار باید مقدار، عنصر، چرخه، اپراتور، قاعده و علت را نشان دهد.
- سیستم باید امکان بازبینی هم‌زمان چند مشاهده را داشته باشد.
- تشخیص آماری به‌تنهایی دلیل فنی حذف داده نیست؛ شرایط واقعی مشاهده باید بررسی شود.

## FR-19 ـ مقایسه اپراتورها

برای هر فعالیت/عنصر، جدول و نمودار مقایسه اپراتورها ارائه شود:

- تعداد مشاهدات معتبر
- میانگین مشاهده‌شده
- انحراف معیار و CV
- ضریب وستینگهاوس مشترک عنصر
- زمان نرمال
- زمان استاندارد عنصر
- تعداد داده‌های مشکوک/خارج‌شده

از آنجا که ارزیابی وستینگهاوس در تصمیم فعلی در سطح عنصر کاری مشترک است، مقدار R برای همه اپراتورها یکسان است. تفاوت زمان نرمال اپراتورها از میانگین مشاهده‌شده آن‌ها ناشی می‌شود.

## FR-20 ـ OPC/FPC

- یک بخش مستقل «نمودار فرایند» وجود داشته باشد و کاربر بین OPC و FPC جابه‌جا شود.
- گره‌های پایه از فعالیت‌های تعریف‌شده تولید شوند.
- OPC عملیات و بازرسی را نشان دهد.
- FPC عملیات، بازرسی، حمل‌ونقل، تأخیر و انبارش را پوشش دهد.
- گره‌های اضافی بدون فعالیت زمان‌سنجی مستقیم، دستی قابل ایجاد و ویرایش باشند.
- نمودار چیدمان خودکار اولیه داشته باشد.
- کاربر بتواند گره‌ها را جابه‌جا کند و چیدمان دستی حفظ شود.
- هر گره و ارتباط با شناسه پایدار ذخیره شود؛ ارتباط نباید صرفاً بر اساس نام فعالیت باشد.
- حذف یا تغییر نمودار نباید مشاهدات زمان‌سنجی را حذف کند.
- حذف فعالیت طبق تصمیم حذف دائمی اطلاعات وابسته، داده‌های زمان‌سنجی آن فعالیت را نیز حذف می‌کند؛ گره‌های وابسته خودکار آن فعالیت نیز حذف/پاک‌سازی شوند. گره‌های مستقل دستی نباید بی‌دلیل حذف شوند.

## FR-21 ـ داشبورد تحلیل

- ابتدا کارت‌های خلاصه: زمان استاندارد (در صورت قابل محاسبه بودن)، میانگین، تعداد نمونه و وضعیت هدف نمونه.
- نمودارها و شاخص‌های تخصصی در بخش‌های بازشونده/قابل گسترش قرار بگیرند.
- کاربر بتواند کارت‌ها، شاخص‌ها و نمودارها را فعال/غیرفعال و مرتب کند.
- چیدمان شخصی‌سازی‌شده ذخیره شود.
- در داده ناقص/غیرقابل محاسبه، کارت باید علت را نشان دهد؛ نمایش صفر یا مقدار ساختگی ممنوع است.

## FR-22 ـ گزارش و خروجی

- خروجی Excel برای تحلیل داده‌ها.
- خروجی PDF برای گزارش رسمی/چاپ.
- خروجی سریع در صفحه‌های مرتبط.
- مرکز جامع گزارش‌ها برای انتخاب پروژه، ایستگاه، فعالیت، اپراتور و نوع گزارش.
- گزارش شامل پارامترها و فرض‌های محاسبات، روش کرنومتر، تعداد نمونه، داده‌های خارج‌شده، جدول وستینگهاوس، دسته‌های مجاز و فرمول زمان استاندارد باشد.
- فایل خروجی باید فارسی/RTL را درست نمایش دهد و ارقام/تاریخ مطابق تنظیمات باشند.
- گزارش نباید نتیجه‌ای را که نیازمند بازبینی است به‌عنوان استاندارد قطعی معرفی کند.

## FR-23 ـ ذخیره خودکار و وضعیت ذخیره

وضعیت‌های رابط:

- در حال ذخیره
- ذخیره شد
- خطا در ذخیره‌سازی

- هر تغییر مهم باید به Backend ارسال شود.
- ذخیره‌سازی سلول‌ها باید با batching مناسب، جلوگیری از درخواست‌های تکراری و مدیریت هم‌زمانی انجام شود؛ «پس از هر تغییر» به معنی ارسال غیرضروری یک درخواست برای هر کلید فشرده‌شده نیست.
- تغییرات در صف ذخیره نباید هنگام جابه‌جایی صفحه از بین بروند.
- اگر ذخیره شکست خورد، داده محلی موقت حفظ و اقدام Retry واضح ارائه شود.
- هیچ پیام موفقیت قبل از تأیید Backend نمایش داده نشود.

## FR-24 ـ پشتیبان‌گیری و بازیابی

- پشتیبان‌گیری خودکار با زمان‌بندی قابل تنظیم.
- پشتیبان‌گیری دستی با انتخاب مقصد.
- بازیابی از نسخه پشتیبان با نمایش تاریخ، اندازه، نسخه ساختار داده و نام پروژه/پایگاه.
- پشتیبان باید داده‌ها، تنظیمات، نمودارها و فایل‌های پیوست را در صورت وجود پوشش دهد.
- از کپی خام فایل پایگاه داده در حین نوشتن خودداری شود؛ از API/روش رسمی و سازگار موتور پایگاه داده برای snapshot استفاده شود.
- پیش از بازیابی، پشتیبان فعلی به‌صورت خودکار گرفته شود.
- پس از بازیابی، integrity check و migration لازم اجرا شود.
- در حالت بازیابی، تأیید صریح کاربر و توضیح اثر جایگزینی داده‌ها الزامی است.

## FR-25 ـ بسته خروجی کامل پروژه

- کل پروژه در یک بسته اختصاصی نسخه‌دار قابل خروجی باشد.
- بسته شامل manifest، اطلاعات پروژه، ساختار، تنظیمات، گروه‌های مجاز، داده‌های خام، ارزیابی وستینگهاوس، نمودارها، تاریخچه مجاز و فایل‌های پیوست باشد.
- بسته دارای نسخه schema و checksum برای تشخیص خرابی باشد.
- ورود بسته به‌صورت پیش‌فرض پروژه جدید ایجاد کند و پروژه موجود را بازنویسی نکند.
- قبل از واردکردن، اعتبارسنجی ساختار، شناسه‌ها، نسخه و صحت فایل‌ها انجام شود.
- هیچ کد اجرایی/اسکریپت ناشناخته‌ای از بسته اجرا نشود.

## FR-26 ـ حذف دائمی

- حذف ایستگاه، فعالیت یا عنصر کاری فقط پس از نمایش تعداد و نوع داده‌های وابسته و تأیید صریح مجاز باشد.
- عملیات حذف وابستگی‌ها باید در یک تراکنش اتمیک اجرا شود؛ در صورت خطا، هیچ حذف نیمه‌کاره باقی نماند.
- مطابق تصمیم کاربر، حذف در پایگاه داده عملیاتی دائمی است و سطل بازیافت ایجاد نمی‌شود.
- برای حفظ قابلیت پیگیری، فقط رویداد حداقلی حذف شامل نوع موجودیت، شناسه، زمان و عامل محلی ثبت شود؛ محتوای حذف‌شده در Audit Log کپی نشود.
- اگر پشتیبان‌های قبلی حاوی داده حذف‌شده باشند، سیاست پاک‌سازی/چرخش پشتیبان باید در UI و مستندات روشن باشد. در بازیابی، ثبت حداقلی حذف‌ها باید از بازگرداندن ناخواسته همان داده‌ها جلوگیری کند یا کاربر به‌طور واضح از بازگردانی نسخه قدیمی آگاه شود.

## FR-27 ـ تاریخچه تغییرات و نهایی‌سازی

- وضعیت پروژه/مطالعه می‌تواند نهایی‌شده باشد، اما ویرایش قفل نشود.
- تغییر اطلاعات مؤثر بر محاسبات، نتیجه قبلی را «نیازمند محاسبه مجدد» کند.
- تاریخ آخرین محاسبه و آخرین تغییر نمایش داده شود.
- تاریخچه تغییرات مهم، زمان، نوع موجودیت، شناسه، مقدار قبل و بعد و عامل محلی را ثبت کند.
- محاسبه‌ها به‌صورت snapshot نسخه‌دار با نسخه فرمول و تنظیمات مورد استفاده حفظ شوند.
- در صورت حذف دائمی، Audit نباید محتوای حذف‌شده را باز نگه دارد.

## FR-28 ـ راهنما و آموزش

- کنار عنوان‌ها، فیلدها، جداول و فرایندهای مهم آیکون راهنما قرار گیرد.
- کلیک روی آیکون، پنجره کوچک حاوی توضیح روشن، مثال صنعتی و نکته مهم باز کند.
- فهرست راهنمای مراحل در کنار صفحه باشد و قابلیت باز/جمع شدن داشته باشد.
- در هر مرحله اقدام بعدی پیشنهاد شود.
- در اولین استفاده، راهنمای تعاملی و برجسته‌سازی کنترل‌ها می‌تواند نمایش داده شود؛ امکان ردکردن و اجرای مجدد لازم است.
- راهنمای هر قسمت از محتوای واقعی همان فیلد/قانون استفاده کند؛ توضیحات کلی و مبهم پذیرفته نیست.

## FR-29 ـ زبان، تاریخ و تم

- پیش‌فرض فارسی، راست‌چین، تقویم شمسی و ارقام فارسی باشد.
- امکان تغییر زبان، تقویم و نوع ارقام از تنظیمات نرم‌افزار وجود داشته باشد.
- داده تاریخ در پایگاه داده با قالب استاندارد و بدون وابستگی به نمایش شمسی ذخیره شود؛ تبدیل شمسی/میلادی در لایه نمایش انجام شود.
- ورودی ارقام فارسی و لاتین پذیرفته شود.
- تم روشن و تیره هر دو موجود و قابل انتخاب باشند.
- رابط در هر دو تم کنتراست و خوانایی مناسب داشته باشد.

## FR-30 ـ واکنش‌گرایی و تعامل

- اولویت طراحی برابر برای کامپیوتر، تبلت و موبایل است.
- در دسکتاپ، جدول کامل شبیه Excel نمایش داده شود.
- در موبایل، چرخه‌ها به کارت/فرم تبدیل شوند.
- راهنمای مراحل در موبایل به شکل پنل جمع‌شونده باشد.
- پیام‌ها کوتاه، دوستانه و کم‌مزاحمت باشند.
- هشدار مهم باید علت، اثر و اقدام پیشنهادی داشته باشد.
- انیمیشن‌ها ظریف و هدفمند باشند؛ انیمیشن نباید کار را کند یا مانع دسترسی‌پذیری شود.
- استفاده از رنگ به‌تنهایی برای وضعیت کافی نیست؛ آیکون و متن نیز لازم است.

# بخش ۵ ـ گردش کار کاربر

۱. کاربر صفحه پروژه‌ها را باز می‌کند.  
۲. پروژه جدید می‌سازد و نام، خط، محصول و تاریخ را ثبت می‌کند.  
۳. ایستگاه‌ها را اضافه و با Drag & Drop مرتب می‌کند.  
۴. داخل هر ایستگاه فعالیت‌ها را می‌سازد، نوع فرایند و گروه مجاز را مشخص می‌کند.  
۵. برای هر فعالیت عناصر کاری را تعریف و نوع هر عنصر را تعیین می‌کند.  
۶. اپراتورها را معرفی می‌کند.  
۷. وارد برگه زمان‌سنجی فعالیت می‌شود، اپراتور را انتخاب و جلسه جدید می‌سازد.  
۸. روش کرنومتر را انتخاب می‌کند: برگشت به صفر یا پیوسته.  
۹. چرخه‌ها را در جدول وارد یا از Excel Paste می‌کند.  
۱۰. برای عناصر هم‌زمان، بازه‌های زمانی را در جزئیات سلول/چرخه ثبت می‌کند.  
۱۱. نرم‌افزار خطاهای ورودی و داده‌های مشکوک را نمایش می‌دهد. کاربر داده‌ها را بررسی می‌کند.  
۱۲. تعداد نمونه هدف را بررسی و در صورت کمبود، دلیل نهایی‌سازی را ثبت می‌کند.  
۱۳. ارزیابی وستینگهاوس را برای هر عنصر ثبت می‌کند.  
۱۴. دسته‌های مجاز گروه و مقادیر اختصاصی فعالیت را کنترل می‌کند.  
۱۵. تنظیمات فرمول زمان استاندارد را کنترل می‌کند.  
۱۶. داشبورد تحلیل و مقایسه اپراتورها را مشاهده می‌کند.  
۱۷. OPC/FPC را بازبینی و گره‌های اضافی را در صورت نیاز اضافه می‌کند.  
۱۸. گزارش Excel/PDF تهیه می‌کند.  
۱۹. مطالعه را نهایی می‌کند؛ اما امکان ویرایش بعدی باقی می‌ماند.  
۲۰. پس از هر تغییر مؤثر، نرم‌افزار نتیجه را نیازمند محاسبه مجدد نشان می‌دهد.

# بخش ۶ ـ معماری فنی پیشنهادی

## ۶.۱. معماری منطقی

معماری پیشنهادی یک برنامه وب محلی با لایه‌های جداگانه است:

```text
Browser (Desktop / Tablet / Mobile)
        |
        | HTTPS / Internal LAN
        v
Frontend: React + TypeScript + Vite
        |
        | REST API (JSON)
        v
Backend: ASP.NET Core Web API (.NET 10 LTS)
        |
        +-- Application Services
        |      +-- Project Management
        |      +-- Time Study / Observations
        |      +-- Calculation Engine
        |      +-- Statistics / Outlier Analysis
        |      +-- OPC / FPC
        |      +-- Reports / Export
        |      +-- Backup / Restore
        |      +-- Audit / Settings
        |
        +-- Domain Layer
        |
        +-- Infrastructure Layer
               +-- Entity Framework Core
               +-- SQLite (local disk on same host)
               +-- Local file storage (backups / attachments)
```

## ۶.۲. پشته فنی مرجع

پیشنهاد مرجع برای پیاده‌سازی:

- **Frontend:** React + TypeScript + Vite.
- **Backend:** ASP.NET Core Web API با .NET 10 LTS.
- **ORM:** Entity Framework Core با migrationهای نسخه‌دار.
- **Database اولیه:** SQLite روی دیسک محلی همان میزبان Backend.
- **API:** REST/JSON با قراردادهای تایپ‌شده و نسخه‌بندی.
- **UI:** طراحی کامپوننت‌محور، RTL-first و قابل استفاده آفلاین.
- **Export:** کتابخانه‌های محلی و سازگار با مجوز استفاده تجاری برای Excel و PDF.
- **Charts:** کتابخانه نمودار محلی و بدون CDN.
- **Grid:** کتابخانه جدول یا پیاده‌سازی مناسب با پشتیبانی واقعی از keyboard navigation، clipboard و undo/redo.

.NET 10 در تاریخ تدوین این سند نسخه LTS فعال است؛ سیاست رسمی مایکروسافت پشتیبانی آن را تا نوامبر ۲۰۲۸ اعلام کرده است. نسخه دقیق SDK و بسته‌ها باید در زمان شروع فاز صفر از منبع رسمی بررسی و در پروژه pin شود.

**قید پایگاه داده:** SQLite برای نصب تک‌میزبان و بار نوشتن محدود مناسب است. اگر چند کلاینت از طریق API به یک Backend واحد وصل شوند، فایل SQLite همچنان روی همان سرور و در دسترس همان Backend است؛ کلاینت‌ها نباید فایل DB را مستقیم باز کنند. اگر تعداد نویسندگان هم‌زمان یا نیاز عملیاتی افزایش یافت، PostgreSQL گزینه مهاجرت است. SQLite WAL روی فایل‌سیستم شبکه‌ای پشتیبانی نمی‌شود؛ فایل DB را روی SMB/NAS/Network Share قرار ندهید.

## ۶.۳. مرزبندی لایه‌ها

- **Presentation:** فقط نمایش، دریافت ورودی و اعتبارسنجی اولیه؛ فاقد فرمول مهندسی مستقل.
- **Application:** گردش کار، مجوز عملیات، هماهنگی تراکنش‌ها و فراخوانی سرویس‌ها.
- **Domain:** موجودیت‌ها، قوانین زمان‌سنجی، نوع رویداد، قواعد معتبر بودن چرخه و قرارداد محاسبات.
- **Calculation Engine:** توابع خالص، مستقل از UI و پایگاه داده؛ با آزمون واحد و ورودی/خروجی قابل تکرار.
- **Infrastructure:** ذخیره‌سازی، فایل، پشتیبان، migration و سرویس‌های سیستم.

فرمول‌ها نباید در کامپوننت‌های React یا SQL پراکنده شوند. محاسبات اصلی باید در Backend و ماژول مستقل انجام شوند.

## ۶.۴. مدل داده پیشنهادی

شناسه داخلی تمام موجودیت‌ها باید پایدار باشد (ترجیحاً UUID). نام و ترتیب نمایشی شناسه محسوب نمی‌شوند.

| موجودیت | فیلدهای کلیدی پیشنهادی | ارتباط |
|---|---|---|
| Project | Id, Name, LineName, ProductName, StudyDate, Status, CreatedAt, UpdatedAt | ریشه تمام اطلاعات پروژه |
| ProjectSetting | Id, ProjectId, Key, Value, Version | تنظیمات اختصاصی پروژه |
| Station | Id, ProjectId, Name, Description, SortOrder | متعلق به پروژه |
| ActivityGroup | Id, ProjectId, Name, Description | گروه مجازها |
| Activity | Id, StationId, GroupId, Name, Description, ProcessType, SortOrder, TargetSampleCount | متعلق به ایستگاه |
| AllowanceCategory | Id, ProjectId, Name, Code, IsActive | دسته مجاز |
| GroupAllowance | Id, GroupId, CategoryId, PercentValue | مقدار گروه |
| ActivityAllowanceOverride | Id, ActivityId, CategoryId, PercentValue, IsOverridden | بازنویسی فعالیت |
| WorkElement | Id, ActivityId, Name, Description, ElementType, SortOrder | عنصر کاری فعالیت |
| Operator | Id, ProjectId, DisplayName, Code | اپراتور پروژه |
| StudySession | Id, ActivityId, OperatorId, TimingMethod, StartedAt, Notes, Status | یک جلسه فعالیت/اپراتور |
| CycleObservation | Id, SessionId, CycleNo, ObservedAt, IsComplete, Notes | یک چرخه |
| TimelineLane | Id, CycleId, LaneType, Label | خط زمانی اپراتور/ماشین یا خط دیگر |
| ElementObservation | Id, CycleId, WorkElementId, RawDuration, CumulativeReading, StartOffset, EndOffset, LaneId, ValidityStatus, ExclusionReason | مشاهده عنصر در چرخه |
| RatingTable | Id, ProjectId, Name, Version, Source, IsDefault | جدول مرجع وستینگهاوس |
| RatingAssessment | Id, WorkElementId, RatingTableId, SkillScore, EffortScore, ConditionsScore, ConsistencyScore, TotalFactor | یک ارزیابی برای عنصر |
| CalculationRun | Id, ProjectId, CreatedAt, FormulaVersion, SettingsSnapshot, Status, ResultSnapshot | نتیجه محاسبه نسخه‌دار |
| ChartNode | Id, ProjectId, ChartType, NodeType, ActivityId, Label, PositionX, PositionY, IsManual, SortOrder | گره OPC/FPC |
| ChartEdge | Id, ChartId/ProjectId, SourceNodeId, TargetNodeId, SortOrder | اتصال گره‌ها |
| AuditEvent | Id, EntityType, EntityId, Action, BeforeJson, AfterJson, OccurredAt, Actor | تاریخچه تغییرات |
| DeletionMarker | Id, EntityType, EntityId, DeletedAt | جلوگیری از بازگردانی ناخواسته از پشتیبان |

### قواعد مدل داده

- `Activity` گروه مجازها را می‌شناسد؛ مقدارهای اختصاصی در جدول Override ذخیره می‌شوند.
- `WorkElement` مستقل از نام و ترتیب نمایشی شناسه دارد.
- `StudySession` روش اندازه‌گیری را تثبیت می‌کند؛ تغییر روش برای جلسه موجود مجاز نباشد، بلکه جلسه جدید ساخته شود.
- `ElementObservation` داده خام و وضعیت محاسباتی را جدا نگه می‌دارد.
- برای روش continuous هم قرائت تجمعی و هم مقدار تفاضلی مشتق‌شده نگهداری/قابل بازسازی باشد.
- برای کار هم‌زمان، StartOffset/EndOffset نسبت به مبدأ چرخه و Lane مستقل ذخیره شود.
- `RatingAssessment` در سطح عنصر کاری است و برای تمام اپراتورها/مشاهدات همان عنصر اعمال می‌شود.
- `CalculationRun` snapshot تنظیمات و نسخه فرمول را ذخیره می‌کند تا نتیجه تاریخی قابل بازتولید باشد.
- `ChartNode.ActivityId` باید nullable باشد تا گره دستی مستقل نیز پشتیبانی شود.
- حذف دائمی با کلیدهای خارجی و تراکنش کنترل‌شده اجرا شود؛ رفتار cascade برای هر موجودیت صریح و آزموده باشد.

## ۶.۵. APIهای اصلی پیشنهادی

نام‌گذاری نهایی می‌تواند با سبک کد هماهنگ شود؛ اما دامنه API باید حداقل این عملیات را پوشش دهد:

GET/POST/PUT/DELETE /api/projects/{projectId}/stations
GET/POST/PUT/DELETE /api/stations/{stationId}/activities
GET/POST/PUT/DELETE /api/activities/{activityId}/elements

API باید DTO مستقل از مدل EF داشته باشد، خطاهای اعتبارسنجی ساختاریافته برگرداند و پیام خطا برای رابط فارسی قابل تبدیل باشد.

## ۶.۶. ذخیره خودکار و هم‌زمانی

- هر درخواست نوشتن باید transaction و شناسه تغییر/درخواست داشته باشد.
- API باید برای عملیات قابل تکرار، idempotency یا سازوکار جلوگیری از ثبت دوباره داشته باشد.
- از نسخه رکورد/UpdatedAt یا RowVersion برای جلوگیری از overwrite ناخواسته استفاده شود.
- ذخیره‌سازی سلول‌های جدول می‌تواند با تأخیر کوتاه و batching انجام شود؛ آخرین وضعیت قبل از خروج از صفحه flush شود.
- در قطع ارتباط با Backend، ورودی‌های تأییدنشده در حافظه محلی/صف موقت نگه داشته و وضعیت خطا نمایش داده شود؛ پس از اتصال مجدد Retry انجام شود.
- صف ذخیره باید ترتیب تغییرات یک رکورد را حفظ کند.

## ۶.۷. پشتیبان و فایل

ساختار پیشنهادی:

```text
/app-data/
  database/             # فایل DB روی دیسک محلی میزبان
  backups/              # نسخه‌های خودکار و دستی
  project-packages/     # فایل‌های export پروژه
  attachments/          # تصاویر/فایل‌های پیوست، در صورت فعال بودن
  logs/                 # لاگ فنی بدون داده حساس غیرضروری
```

- مسیر واقعی در تنظیمات استقرار مشخص شود.
- دسترسی پوشه فقط برای حساب سیستم‌عامل اجرای سرویس مجاز باشد.
- backup در همان پوشه‌ای که DB فعال است تنها نسخه پشتیبان محسوب نشود؛ حداقل امکان مقصد دوم روی فضای داخلی مجزا وجود داشته باشد.
- فایل پشتیبان checksum داشته باشد.
- Restore قبل از جایگزینی، backup حفاظتی بگیرد.
- بازیابی بعد از اعتبارسنجی و در وضعیت خاموش/کنترل‌شده سرویس انجام شود.

## ۶.۸. امنیت و حریم داده

- سرویس فقط به Loopback یا رابط شبکه داخلی موردنیاز bind شود؛ به‌صورت پیش‌فرض روی همه رابط‌های عمومی باز نشود.
- Firewall دسترسی را به شبکه/دستگاه مجاز محدود کند.
- در صورت عبور اعتبارنامه/داده حساس در شبکه داخلی، HTTPS با گواهی سازمانی یا گواهی محلی معتبر تنظیم شود.
- CORS فقط Origin برنامه را بپذیرد.
- اعتبارسنجی سمت سرور الزامی است؛ اعتبارسنجی Frontend به‌تنهایی کافی نیست.
- فایل‌های ورودی محدودیت نوع، اندازه و بررسی ساختار داشته باشند.
- از اجرای محتوا/اسکریپت داخل فایل واردشده خودداری شود.
- لاگ‌ها شامل اطلاعات غیرضروری اپراتور یا داده تولیدی خام نباشند.
- هیچ Telemetry، تحلیل رفتار یا تماس خارجی پنهان وجود نداشته باشد.

## ۶.۹. کارکرد بدون اینترنت

- فونت، آیکون، CSS، JS، نمودار و کتابخانه‌ها از منابع خارجی بارگذاری نشوند.
- برنامه پس از نصب، با قطع کامل اینترنت عمومی همچنان تمام قابلیت‌های تعریف‌شده را اجرا کند.
- فرایند Build/Deploy باید بسته‌های موردنیاز را محلی داشته باشد یا روش نصب آفلاین مستند ارائه کند.
- در آزمون پذیرش، دسترسی اینترنت عمومی مسدود شود و عملکرد کل برنامه دوباره بررسی شود.

# بخش ۷ ـ معماری رابط کاربری و طراحی تعامل

## ۷.۱. صفحه اصلی

کارت پروژه‌ها با اطلاعات: نام، خط، محصول، تاریخ، وضعیت و درصد پیشرفت. دکمه واضح «پروژه جدید» و جست‌وجو/مرتب‌سازی.

## ۷.۲. پوسته پروژه

- Sidebar جمع‌شونده شامل مراحل پروژه.

- نوار راهنمای مرحله‌ای در کنار صفحه؛ جمع‌شونده.
- فضای کاری اصلی برای فرم/جدول/نمودار.

## ۷.۳. درخت ساختار تولید

درخت خط، ایستگاه و فعالیت نمایش داده شود. افزودن/حذف/مرتب‌سازی بدون بارگذاری غیرضروری کل صفحه ممکن باشد. انتخاب گره، فضای محتوای مرتبط را به‌روزرسانی کند.

## ۷.۴. رفتار جدول زمان‌سنجی

- سلول فعال با کنتراست واضح.
- Paste چندسلولی با پیش‌نمایش و تطبیق ستون‌ها.
- Undo/Redo مستقل و قابل پیش‌بینی.
- ردیف ناقص و مقدار نامعتبر با مرزبندی و متن خطا مشخص شود.
- وضعیت مشاهده با رنگ ملایم + آیکون + متن قابل دسترسی باشد.
- اطلاعات جزئی هشدار با کلیک باز شود.
- ستون شناسه چرخه، شماره چرخه و زمان ثبت به‌صورت مناسب در دسترس باشد.
- در جدول بزرگ، سربرگ و ستون‌های کلیدی می‌توانند ثابت بمانند؛ رفتار RTL و اسکرول آزموده شود.

## ۷.۵. راهنما

- «چه چیزی وارد کنم؟» راهنمای ورودی.
- «مثال» با مثال صنعتی واقعی‌نما.
- «نکته مهم» برای خطای رایج یا اثر محاسباتی.

## ۷.۶. پیام‌های سیستم

- هشدار: علت + پیامد + اقدام پیشنهادی.
- خطا: توضیح قابل فهم + شناسه خطای فنی در جزئیات/لاگ.

- ذخیره: نشانگر پایدار و غیرمزاحم.

# بخش ۸ ـ قواعد عددی، واحدها و صحت محاسبات

## ۸.۱. واحد و دقت

- واحد پایه داخلی زمان: ثانیه.
- نمایش پیش‌فرض: دو رقم اعشار.
- گردکردن فقط در لایه نمایش/خروجی انجام شود؛ مقدار خام و مقدار محاسباتی با دقت بالاتر باقی بمانند.
- محاسبات مالی نیستند؛ برای زمان و ضرایب، نوع عددی دقیق و کنترل‌شده انتخاب شود (ترجیحاً decimal در محاسبات پایه).
- تبدیل دقیقه/ساعت در لایه نمایش انجام شود و واحد در هر گزارش صریح باشد.

## ۸.۲. اعتبارسنجی

- زمان منفی ممنوع.
- مقدار عددی خالی با صفر یکسان نیست.
- صفر فقط در جاهایی مجاز است که از نظر نوع عنصر و معنا قابل قبول باشد؛ مثلاً یک خانه زمان مشاهده معمولاً باید مثبت باشد.
- قرائت پیوسته در هر Lane باید صعودی یا مساوی با قواعد روشن باشد؛ مدت صفر برای عنصر عادی هشدار/خطا است.
- پایان بازه باید بزرگ‌تر از شروع باشد.
- StartOffset نباید منفی باشد مگر مدل چرخه صراحتاً اجازه مبدأ جابه‌جا داشته باشد.
- عناصر اجباری ناقص، چرخه را از «چرخه کامل معتبر» خارج می‌کنند؛ داده‌های ناقص همچنان قابل مشاهده‌اند.

## ۸.۳. تست‌های مرجع محاسبات

این تست‌ها باید در موتور محاسبات پیاده‌سازی و خودکار اجرا شوند:

**تست وستینگهاوس:**

- Skill = +0.06
- Effort = +0.02
- Conditions = 0
- Consistency = +0.01
- مجموع = +0.09، بنابراین `R = 1.09`.
- اگر OT = 8.30 ثانیه باشد، `NT = 8.30 × 1.09 = 9.047` ثانیه.

**تست دو مبنای مجاز:**

اگر NT = 9.047 و A = 0.15:

- مبنای زمان نرمال: `ST = 9.047 × 1.15 = 10.40405` ثانیه.
- مبنای سهم از زمان استاندارد: `ST = 9.047 / 0.85 ≈ 10.643529` ثانیه.

**تست روش پیوسته:**

قرائت‌های تجمعی ۸، ۲۰، ۴۵ ثانیه باید زمان‌های ۸، ۱۲ و ۲۵ ثانیه تولید کنند.

**تست هم‌پوشانی:**

- کار اپراتور: بازه [۰، ۸]
- کار خودکار ماشین: بازه [۵، ۲۵]
- مجموع مدت عناصر = ۲۸ ثانیه
- زمان سپری‌شده = ۲۵ ثانیه

نرم‌افزار نباید ۲۸ ثانیه را زمان سپری‌شده چرخه گزارش کند.

**تست دقت نمایش:**

مقدار داخلی ۱۲٫۳۵۷ باید در نمایش پیش‌فرض ۱۲٫۳۶ (با قاعده گردکردن صریح و یکسان) نشان داده شود، بدون تغییر مقدار ذخیره‌شده.

# بخش ۹ ـ آزمون، کیفیت و معیارهای پذیرش

## ۹.۱. لایه‌های آزمون

۱. Unit Test برای فرمول‌ها، قواعد اعتبارسنجی و تبدیل روش‌ها.  
۲. Integration Test برای API، پایگاه داده، تراکنش، Backup/Restore و Import/Export.  
۳. UI/E2E Test برای گردش اصلی کاربر، جدول و RTL.  
۴. Regression Test برای جلوگیری از خرابی قابلیت‌های قبلی.  
۵. Offline Test با مسدودکردن اینترنت عمومی.  
۶. Recovery Test با قطع برنامه، خرابی فایل ورودی و بازیابی نسخه پشتیبان.

## ۹.۲. معیار پذیرش کلی

نسخه اول تنها وقتی قابل تحویل است که:

- تمام FRهای این سند پیاده‌سازی شده باشند یا هر مورد اختلاف با تأیید کتبی مالک محصول تعیین تکلیف شود.
- آزمون‌های فرمولی بخش ۸ موفق باشند.
- جدول زمان‌سنجی در ورودی دستی و Paste درست کار کند.
- روش پیوسته و برگشت به صفر از هم تفکیک و درست محاسبه شوند.
- هم‌زمانی به‌صورت بازه زمانی نگهداری شود و زمان سپری‌شده اشتباه نشود.
- تغییرات بعد از نهایی‌سازی، نتیجه را نیازمند محاسبه مجدد کنند.
- نمودارها بعد از ویرایش، چیدمان دستی را حفظ کنند.
- گزارش Excel و PDF در حالت فارسی درست باشند.
- برنامه بدون اینترنت عمومی کار کند.
- backup/restore و export/import کامل آزموده شوند.
- هیچ خطای بحرانی/داده‌گم‌کنی شناخته‌شده باقی نماند.
- مستند نصب، پشتیبان‌گیری، بازیابی، تنظیمات و آزمون تحویل داده شود.

## ۹.۳. Definition of Done برای هر قابلیت

یک قابلیت فقط زمانی «تکمیل» است که:

- کد UI و Backend آن وجود داشته باشد.
- قواعد دامنه و اعتبارسنجی سمت سرور پیاده شده باشد.
- حالت Loading/Empty/Error/Success طراحی شده باشد.
- RTL و واکنش‌گرایی بررسی شده باشد.
- Unit/Integration/E2E متناسب نوشته و اجرا شده باشد.
- راهنمای داخل برنامه و مستند فنی آن به‌روزرسانی شده باشد.
- نتیجه آزمون و محدودیت‌های باقی‌مانده گزارش شده باشد.

# بخش ۱۰ ـ ابهام‌ها و تصمیم‌های محافظه‌کارانه

این قسمت برای جلوگیری از تصمیم‌گیری پنهانی ایجنت است.

## ۱۰.۱. روش تجمیع چند اپراتور

**تصمیم فنی پیش‌فرض:** میانگین تجمیعی عنصر بر اساس تمام مشاهدات معتبر محاسبه شود (هر مشاهده وزن برابر). در کنار آن، آمار هر اپراتور جدا باشد. روش «میانگین اپراتورها با وزن برابر» در تنظیمات پیشرفته به‌عنوان روش جایگزین قابل ارائه باشد. روش انتخابی در گزارش ثبت شود.

## ۱۰.۲. وستینگهاوس مشترک بین اپراتورها

تصمیم فعلی مالک محصول ارزیابی در سطح عنصر کاری و اعمال به تمام مشاهدات همان عنصر است. بنابراین ضریب در مقایسه اپراتورها برای یک عنصر یکسان است. ایجنت نباید بی‌اجازه ارزیابی مستقل اپراتور ایجاد کند.

## ۱۰.۳. استاندارد کل فعالیت دارای کار هم‌زمان

زمان استاندارد عنصرها قابل محاسبه است، اما استاندارد کل چرخه هم‌پوشان نیازمند مدل تقدم‌وتأخر/زمان‌بندی یا سیاست تجمیع مورد تأیید مهندسی است. در نسخه اول، اگر فعالیت هم‌پوشانی دارد و سیاست معتبر تعریف نشده، زمان استاندارد کل فعالیت باید با وضعیت «نیازمند قاعده تجمیع» نمایش داده شود. جمع ساده عناصر ممنوع است. ایجنت باید این محدودیت را واضح در UI و گزارش بنویسد.

## ۱۰.۴. تعداد نمونه و کفایت آماری

کاربر فقط تعداد هدف را تعیین می‌کند. سیستم نباید رسیدن به آن هدف را اثبات کفایت آماری بداند. شاخص‌های پراکندگی و بازه اطمینان می‌توانند کمک کنند، اما هر برچسب «کافی» باید به تعریف روشن و روش آماری مستند متصل باشد. در غیر این صورت از عباراتی مانند «هدف تعداد نمونه تکمیل شد» استفاده شود.

## ۱۰.۵. حذف دائمی و نسخه‌های پشتیبان

حذف از پایگاه عملیاتی دائمی است؛ اما نسخه‌های پشتیبان قدیمی ممکن است تا زمان چرخش حاوی نسخه قبلی اطلاعات باشند. Restore باید DeletionMarkerها را اعمال کند یا نسخه‌ای که داده حذف‌شده را برمی‌گرداند با هشدار روشن معرفی شود. سیاست پاک‌سازی نسخه‌های پشتیبان باید مستند و قابل فهم باشد.

## ۱۰.۶. نام کاربر در تاریخچه

به علت نبود احراز هویت، فقط «کاربر محلی/میزبان» قابل ثبت است؛ نام فرد حقیقی ثبت‌شده و قابل اعتماد نخواهد بود.

# بخش ۱۱ ـ نقشه اجرایی توسعه

تمام فازهای زیر بخشی از نسخه اول هستند. عبور به فاز بعد تنها پس از ارائه شواهد قبولی فاز جاری انجام شود.

## فاز صفر ـ تحلیل و تثبیت فنی

- بررسی محیط توسعه، سیستم‌عامل استقرار و محدودیت شبکه داخلی.
- تأیید معماری پیشنهادی .NET 10 + React/TypeScript + SQLite یا ارائه دلیل فنی جایگزین.
- بررسی مجوز کتابخانه‌های Grid، نمودار، Excel، PDF و Drag & Drop.
- تهیه Architecture Decision Records (ADR).
- تدوین ERD، قرارداد API و نمونه Wireframe.
- تهیه فهرست آزمون‌های فرمولی و ریسک‌های unresolved.
- در این فاز کدنویسی گسترده انجام نشود؛ فقط PoC لازم برای اثبات موارد فنی.

**خروجی فاز صفر:** سند معماری، ERD، API contract، طراحی اولیه UI، فهرست کتابخانه‌های مجاز/دارای مجوز، برنامه آزمون و گزارش ریسک.

## فاز یک ـ زیرساخت، محیط داخلی و مدیریت پروژه

- راه‌اندازی Frontend/Backend.
- تنظیم RTL، زبان و تم.
- راه‌اندازی پایگاه داده و Migration.
- صفحه پروژه‌ها و ایجاد/ویرایش/حذف پروژه.
- ذخیره خودکار پایه، وضعیت ذخیره، ثبت رویداد تغییر.
- Backup/Restore اولیه.
- تست قطع اینترنت و استقرار داخلی.

## فاز دو ـ ساختار تولید و تنظیمات مهندسی

- خط، ایستگاه، فعالیت، گروه فعالیت و عنصر کاری.
- Drag & Drop و درخت ساختار.
- تعریف نوع فعالیت و نوع عنصر کاری.
- مدیریت اپراتورها.
- گروه و دسته‌های مجاز و Override فعالیت.

# بخش ۱۲ ـ دستورالعمل اصلی قابل ارسال به ایجنت توسعه‌دهنده

متن زیر را می‌توان به‌عنوان پیام اصلی به ایجنت ارسال کرد. فایل کامل همین سند را نیز به‌عنوان مرجع ضمیمه کن.

## پرامپت اصلی ایجنت

**نقش تو:** مهندس ارشد نرم‌افزار، معمار سیستم و توسعه‌دهنده مسئول پیاده‌سازی یک وب‌اپلیکیشن حرفه‌ای زمان‌سنجی صنعتی هستی. باید محصول را بر اساس سند مرجع پیوست پیاده‌سازی کنی. سند مرجع، منبع حقیقت نیازمندی‌ها است و تصمیم‌های قطعی آن نباید خودسرانه تغییر کنند.

### ۱. مأموریت

یک وب‌اپلیکیشن داخلی و فارسی برای مدیریت مطالعات زمان‌سنجی خطوط تولید بساز. هر پروژه فقط یک خط تولید و یک محصول دارد. کاربر اصلی یک کارشناس روی یک سیستم است؛ برنامه بدون صفحه ورود و بدون وابستگی زمان اجرا به اینترنت عمومی روی کامپیوتر/سرور داخلی شرکت اجرا می‌شود. برنامه باید داده‌ها را خودکار ذخیره کند، از آن‌ها پشتیبان بگیرد و امکان خروجی/بازیابی کامل پروژه را فراهم کند.

### ۲. مرجع و تقدم تصمیم‌ها

۱. فایل PRD/معماری پیوست را کامل بخوان و تمام شناسه‌های FR و قواعد آن را به نیازمندی قابل آزمون تبدیل کن.  
۲. تصمیم‌های قطعی مالک محصول در سند از سلیقه فنی تو بالاترند.  
۳. پیشنهاد فنی فقط وقتی قابل تغییر است که ناسازگاری واقعی یا ریسک مستند داشته باشد؛ قبل از تغییر، ADR شامل دلیل، گزینه‌ها، پیامد و اثر بر نیازمندی‌ها بنویس.  
۴. قابلیت حذف‌شده یا ساده‌شده را بدون تأیید مالک محصول جایگزین نکن.  
۵. هیچ فرمول، نرخ مجاز، جدول وستینگهاوس یا قاعده آماری را بدون ذکر منبع/فرض به‌عنوان استاندارد قطعی معرفی نکن.  
۶. اگر ابهام مهندسی وجود دارد، رفتار محافظه‌کارانه سند را اجرا کن؛ عدد یا فرمول دلخواه نساز و خروجی نامطمئن را قطعی نشان نده.

### ۳. الزامات غیرقابل مذاکره

- رابط فارسی RTL-first و واکنش‌گرا برای دسکتاپ، تبلت و موبایل.
- صفحه اصلی کارت پروژه‌ها.
- منوی کناری مراحل با وضعیت چهارگانه و امکان جابه‌جایی آزاد.
- درخت خط/ایستگاه/فعالیت.
- صفحه فعالیت با زبانه‌های مشخصات، عناصر کاری، زمان‌سنجی و تحلیل.
- جدول هر فعالیت: هر ردیف چرخه، هر ستون عنصر کاری.
- اپراتورهای متعدد با برگه جداگانه برای هر اپراتور.
- ورود دستی و Paste چندسلولی Excel؛ کرنومتر داخلی نساز.
- هر دو روش Snapback و Continuous.
- ثبت بازه‌های مستقل برای عناصر هم‌زمان اپراتور و ماشین؛ جمع مدت‌های هم‌پوشان را زمان سپری‌شده چرخه تلقی نکن.
- تشخیص داده مشکوک فقط هشدار است؛ حذف از محاسبه فقط با تصمیم کاربر و حفظ داده خام.
- Westinghouse در سطح عنصر کاری و مشترک برای تمام مشاهدات همان عنصر.
- مجازهای دسته‌بندی‌شده در گروه و Override در فعالیت.
- هر دو فرمول مجاز و نمایش فرمول نهایی در گزارش.
- OPC/FPC خودکار + گره اضافی دستی + حفظ چیدمان کاربر.
- داشبورد خلاصه + شاخص‌های تخصصی قابل شخصی‌سازی.
- Excel/PDF.
- تم روشن و تیره، راهنمای آیکونی، فهرست مراحل جمع‌شونده، پیام‌های دوستانه و کم‌مزاحمت.
- ذخیره خودکار، Backup/Restore، بسته کامل پروژه، کپی پروژه و حذف دائمی تأییدشده.
- تاریخچه تغییرات و نیازمند محاسبه مجدد شدن نتایج پس از تغییر.
- هیچ تماس خارجی در زمان اجرا.

### ۴. معماری مرجع

در صورت نبود مانع مستند، از React + TypeScript + Vite برای Frontend، ASP.NET Core Web API با .NET 10 LTS برای Backend، Entity Framework Core برای دسترسی داده و SQLite روی دیسک محلی همان میزبان Backend استفاده کن. فایل SQLite را روی پوشه شبکه قرار نده. مرورگرهای شبکه داخلی فقط با API صحبت کنند. وابستگی‌های UI، فونت، آیکون، نمودار و Export باید محلی باشند.

لایه‌های Presentation، Application، Domain، Calculation و Infrastructure را جدا نگه دار. منطق محاسبه در Backend و ماژول مستقل با توابع قابل آزمون قرار بگیرد؛ فرمول را در UI یا SQL پراکنده نکن.

### ۵. قواعد محاسباتی حیاتی

- `R = 1 + Skill + Effort + Conditions + Consistency`
- `NT = OT × R`
- allowance method 1: `ST = NT × (1 + A)`
- allowance method 2: `ST = NT / (1 - A)` و در این روش `A < 1` الزامی است.
- Continuous: زمان عنصر = قرائت تجمعی فعلی − قرائت تجمعی قبلی در همان Lane.
- Parallel: مدت هر بازه = پایان − شروع؛ زمان سپری‌شده چرخه از گستره بازه‌ها به دست می‌آید، نه جمع مدت‌های دارای هم‌پوشانی.
- برای فعالیت هم‌پوشان، زمان استاندارد کل فعالیت را با جمع ساده زمان استاندارد عناصر تولید نکن. تا تعیین/تأیید مدل تجمیع، خروجی کل فعالیت «نیازمند قاعده تجمیع» باشد.
- هدف نمونه کاربرمحور است؛ رسیدن به هدف را با کفایت آماری تضمین‌شده یکی نکن.
- Outlier با روش مقاوم پیشنهادی علامت‌گذاری شود؛ هرگز خودکار حذف نشود.
- مقادیر خام و دقت داخلی حفظ شوند؛ دو رقم اعشار فقط نمایش پیش‌فرض است.

### ۶. پروتکل توسعه مرحله‌ای

**پیش از کدنویسی گسترده، فاز صفر را انجام بده:** مخزن/محیط موجود را بررسی کن، معماری و محدودیت استقرار را مستند کن، مجوز کتابخانه‌ها را بررسی کن، ERD، API contract، wireframe، ADR و آزمون‌های مرجع را ارائه بده. اگر مخزن موجود است، ابتدا وضعیت آن را گزارش کن و بدون مجوز، شاخه اصلی یا داده‌های موجود را تخریب نکن.

پس از فاز صفر، پیاده‌سازی را در فازهای زیر انجام بده و هر فاز را با آزمون و گزارش تحویل ببند:

۰. تحلیل و تثبیت فنی.  
۱. زیرساخت، محیط داخلی، پایگاه داده و مدیریت پروژه.  
۲. ساختار تولید، فعالیت، عناصر، اپراتورها و تنظیمات مهندسی.  
۳. برگه زمان‌سنجی، Paste، Snapback، Continuous و هم‌پوشانی.  
۴. کنترل داده، آمار، وستینگهاوس، مجازها و موتور محاسبات.  
۵. OPC/FPC و ویرایش چیدمان.  
۶. داشبورد، گزارش‌ها، راهنما و واکنش‌گرایی.  
۷. سخت‌سازی، پشتیبان/بازیابی، آزمون نهایی و تحویل.

این فازبندی محدوده نسخه اول را کاهش نمی‌دهد؛ تمام نیازمندی‌ها باید پیش از اعلام تحویل نسخه اول تکمیل شوند.

### ۷. قواعد کار با مخزن و کد

- قبل از تغییر، ساختار مخزن، شاخه فعال، وضعیت Git، README، قراردادهای موجود، تست‌ها و فایل‌های تنظیمات را بررسی کن.
- تغییرات کوچک و قابل بازبینی انجام بده؛ بازنویسی گسترده بدون توجیه نکن.
- کد مرده، مسیر آزمایشی و mock را به‌عنوان قابلیت واقعی رها نکن.
- از داده جعلی در محیط تولید استفاده نکن؛ seed فقط داده نمونه آموزشی با برچسب روشن باشد.
- خطاها را پنهان نکن؛ لاگ فنی و پیام کاربر جدا باشند.
- همه ورودی‌ها سمت سرور اعتبارسنجی شوند.
- داده‌های موجود را بدون migration و برنامه برگشت تغییر نده.
- نسخه بسته‌ها را pin و مجوز آن‌ها را بررسی کن.
- رازها، کلیدها و مسیرهای حساس را در Git قرار نده.

### ۸. آزمون‌های اجباری و شواهد

حداقل این موارد را به آزمون خودکار تبدیل کن:

۱. `8.30 × 1.09 = 9.047` برای زمان نرمال.  
۲. با `NT=9.047` و `A=0.15`، روش اول `10.40405` و روش دوم تقریباً `10.643529` ثانیه.  
۳. قرائت‌های پیوسته ۸، ۲۰، ۴۵ باید زمان‌های ۸، ۱۲، ۲۵ بدهند.  
۴. بازه‌های [۰،۸] و [۵،۲۵] مجموع مدت ۲۸ ولی زمان سپری‌شده ۲۵ دارند.  
۵. داده خارج‌شده از محاسبه در داده خام باقی بماند و در میانگین وارد نشود.  
۶. روش Paste ترتیب ستون‌ها را درست تشخیص دهد و خطای سلول را مشخص کند.  
۷. تغییر پارامتر محاسباتی، Snapshot قبلی را حفظ و نتیجه جدید را نیازمند محاسبه مجدد کند.  
۸. بعد از حذف دائمی، داده وابسته در DB عملیاتی حذف شود و Backup/Restore رفتار مستند داشته باشد.  
۹. نمودار پس از جابه‌جایی دستی بسته/باز شود و مختصات کاربر حفظ شده باشد.  
۱۰. برنامه با قطع کامل اینترنت عمومی تمام قابلیت‌های نسخه اول را اجرا کند.

### ۹. معیار پایان هر فاز

در پایان هر فاز این موارد را تحویل بده:

- فهرست نیازمندی‌های انجام‌شده با شناسه FR.
- فایل‌ها/ماژول‌های ایجاد یا تغییر یافته.
- آزمون‌های اجراشده و نتیجه واقعی هر آزمون.
- تصویر/ویدئوی کوتاه یا شواهد قابل مشاهده از UI در صورت وجود.
- موارد ناقص، محدودیت‌ها و ریسک‌های شناخته‌شده.
- دستور اجرای محلی و دستور آزمون.
- به‌روزرسانی README، معماری و فایل وضعیت پروژه.

عبارت «انجام شد» بدون خروجی آزمون، log یا شاهد قابل بررسی پذیرفته نیست. اگر آزمونی اجرا نشده است، صریحاً آن را «اجرانشده» بنویس؛ نتیجه فرضی اعلام نکن.

### ۱۰. کنترل انحراف

پیش از هر فاز، جدول تطبیق «نیازمندی سند ↔ کار برنامه‌ریزی‌شده» بساز. بعد از فاز، همان جدول را با شواهد تکمیل کن. هیچ نیازمندی را حذف، ساده یا جایگزین نکن مگر با ثبت ADR و تأیید مالک محصول. اگر محدودیت فنی مانع اجراست، راه‌حل‌های جایگزین را با مزایا/معایب ارائه بده و تا زمان تصمیم، رفتار امن و غیرگمراه‌کننده را پیاده کن.

### ۱۱. اولین پاسخ مورد انتظار تو

فعلاً کدنویسی اصلی را شروع نکن. ابتدا:

۱. سند مرجع را تأیید کن که کامل خوانده‌ای.  
۲. محیط و مخزن/پروژه موجود را بررسی و خلاصه کن.  
۳. معماری پیشنهادی را با شواهد تأیید یا اصلاح کن.  
۴. ERD، API contract، ساختار پوشه‌ها و wireframe صفحات اصلی را پیشنهاد بده.  
۵. ابهام‌های مهندسی باقی‌مانده را فهرست کن؛ برای هرکدام رفتار محافظه‌کارانه پیش‌فرض و اثر آن را ذکر کن.  
۶. برنامه آزمون و فازبندی را ارائه کن.  
۷. پس از آن، منتظر تأیید مالک محصول برای آغاز پیاده‌سازی گسترده بمان.

**دستور نهایی:** سند مرجع را در طول کل پروژه همراه خود نگه دار. کیفیت واقعی، صحت مهندسی، حفظ داده و تجربه کاربری بر سرعت ظاهری توسعه اولویت دارند. هدف ساخت یک محصول کامل، قابل استفاده و قابل اعتماد است؛ نه صرفاً تولید کد یا نمایش ظاهری صفحات.

**قاعده استفاده از منابع:** جداول Westinghouse، درصدهای مجاز و قواعد آماری باید با نسخه/منبع روشن ثبت شوند. این سند منبع را برای جهت‌گیری مهندسی معرفی می‌کند، اما جایگزین روش مصوب شرکت، توافق کاری یا ارزیابی متخصص زمان‌سنجی نیست.

# پیوست ـ چک‌لیست کوتاه مالک محصول برای بازبینی خروجی ایجنت

- [ ] پروژه فقط یک خط و یک محصول دارد.
- [ ] ساختار درختی و ترتیب قابل تغییر است.
- [ ] هر فعالیت برگه مستقل چرخه‌محور دارد.
- [ ] هر اپراتور برگه جداگانه دارد.
- [ ] Paste چندسلولی Excel سالم است.
- [ ] Snapback و Continuous درست کار می‌کنند.
- [ ] هم‌زمانی اپراتور/ماشین با بازه ثبت می‌شود.
- [ ] هیچ زمان هم‌پوشانی دوباره جمع نمی‌شود.
- [ ] مشاهدات مشکوک خودکار حذف نمی‌شوند.
- [ ] هدف تعداد نمونه با کفایت آماری اشتباه گرفته نمی‌شود.
- [ ] Westinghouse در سطح عنصر و مشترک است.
- [ ] هر دو فرمول مجاز وجود دارد.
- [ ] زمان استاندارد فعالیت هم‌پوشان بدون قاعده معتبر اعلام نمی‌شود.
- [ ] OPC/FPC از فعالیت‌ها ساخته و قابل ویرایش است.
- [ ] چیدمان دستی نمودار حفظ می‌شود.
- [ ] Dashboard و گزارش‌ها قابل تنظیم‌اند.
- [ ] Excel و PDF فارسی صحیح تولید می‌شوند.
- [ ] پس از تغییر، محاسبه مجدد لازم تشخیص داده می‌شود.
- [ ] حذف دائمی با تأیید و حذف وابستگی‌ها انجام می‌شود.
- [ ] Backup/Restore واقعی آزموده شده است.
- [ ] برنامه با اینترنت قطع‌شده کار می‌کند.
- [ ] UI در موبایل، تبلت و دسکتاپ قابل استفاده است.
- [ ] راهنماها توضیح و مثال مرتبط دارند.
- [ ] آزمون‌ها و مستندات تحویل شده‌اند.
