# ADR-011: Snapshot پیکربندی v2 و هسته مشترک موتور فرمول

**وضعیت:** پذیرفته‌شده و پیاده‌سازی‌شده — **تاریخ:** ۳۱ اکتبر ۲۰۲۶ — **فاز:** ۲

## زمینه

فاز ۲ به چهار نیاز هم‌زمان رسید که ساختار فاز ۱ پاسخ مستقیم نداشت:
۱. مدل پارامتر کامل B2 (هر ۱۴ نوع داده + شرط DSL + ویژگی سفارشی) و فرمول‌های **اجراپذیر** (عبارت + AST + قرارداد ورودی) در snapshot — یعنی snapshot v1 (خانواده/پارامتر ساده + فرمول ارجاعی بدون عبارت) کافی نبود.
۲. اشتراک نوع snapshot بین ماژول‌ها (config/params/projects/profiles) بدون شکستن قاعده «domain→domain بین‌ماژول‌ها ممنوع» (ADR-001/ARCHITECTURE §۱٫۲).
۳. ارزیابی شرط‌های visibility/required فرم‌ساز **سمت کاربر** — یعنی همان موتور فرمول باید در UI هم قابل import باشد؛ اما «منطق دامنه در UI ممنوع» و import ماژول در UI ممنوع است.
۴. درس عملی تراکنش: کلاینت سراسری `db` داخل callback تعاملی `$transaction` روی SQLite بن‌بست (deadlock) ایجاد می‌کند.

## تصمیم

۱. **Snapshot v2 با قرارداد نوع در `src/shared/contracts/snapshot.ts`:** ساختار کامل (families با پارامتر B2 کامل + defVersion + archived؛ formulas با expr/ast/inputContract/origin؛ activityModel با workTypes/elementTemplates). **ارتقای v1→v2 فقط هنگام خواندن و فقط در حافظه** (`readSnapshotAsV2`): نرمال‌سازی نمایندگی واحدها (مثل `%`→`percent`)، `defVersion=1` برای تعریف‌های قدیمی، و فرمول‌های ارجاعیِ بدون عبارت، یادداشت صادقانه `availabilityNoteFa` («بدون عبارت اجرایی») می‌گیرند — **هیچ مقداری تبدیل نمی‌شود**. نوشتن همیشه **نسخه جدید append-only** می‌سازد؛ snapshotهای v1 در DB دست‌نخورده می‌مانند.
۲. **موتور فرمول به‌عنوان هسته مشترک خالص در `src/shared/formula/`:** بدون وابستگی به DB/UI/زمان سیستم؛ قطعی؛ آزمون‌پذیر (۴۴ آزمون واحد). هم ماژول‌های سرور (config/params) و هم فرم‌ساز کلاینت آن را import می‌کنند — **منبع واحد ارزیابی**؛ شرط‌های فرم بدون رفت‌وبرگشت API و بدون پیاده‌سازی موازی منطق در UI ارزیابی می‌شوند. این جابه‌جایی از نقشه اولیه (`modules/formula`) مستند شد و در ADR-003 هم انعکاس یافت.
۳. **قرارداد نماد نتیجه فرمول:** کلیدهای سفارشی بدون خط تیره (`f.camelCase`) و ارجاع در عبارت با `<کلید>.result` که در آن خط تیره به زیرخط تبدیل می‌شود (`TS-011` → `TS_011.result`) — چون گرامر DSL خط تیره ندارد و «a-b» تفریق است (ابهام با عملگر تفریق).
۴. **تراکنش‌های تعاملی Prisma فقط با کلاینت `tx` داخل callback:** ریپوها پارامتر tx می‌پذیرند و هر کوئریِ داخل `$transaction(async (tx) => …)` با همان tx اجرا می‌شود؛ استفاده از `db` سراسری داخل callback روی SQLite قفل/deadlock می‌دهد (درس عملی فاز ۲).

## گزینه‌های رد‌شده

- **بازنویسی snapshot به v2 با مهاجرت انبوه:** غیرضروری و پرریسک — snapshotهای v1 به‌درستی با خواندن سازگار می‌شوند و هر نوشتن نسخه v2 جدید می‌سازد.
- **تعریف نوع snapshot در domain ماژول config و import آن از ماژول‌های دیگر:** نقض قاعده domain→domain (قفل‌شده با check-module-boundaries) یا تکرار موازی نوع.
- **موتور فرمول در `modules/formula` + آینه‌ای برای UI:** دو منبع حقیقت ارزیابی و ریسک واگرایی شرط‌های فرم بین سرور/کلاینت.
- **اجازه import ماژول در UI برای ارزیابی شرط:** نقض مستقیم قاعده «منطق دامنه در UI ممنوع».

## پیامدها

✅ قواعد مرزها دست‌نخورده (۰ نقض/۰ چرخه — شاهد `docs/evidence/phase2-tests/boundaries.txt`)؛ مهاجرت صادقانه (بدون ادعای اجرایی‌بودن فرمول ارجاعی قدیمی)؛ ارزیابی شرط فرم سمت کاربر بدون API؛ قطعیت و بازتولیدپذیری با یک موتور.
⚠️ نوع snapshot در `shared` (نه domain ماژول config) زندگی می‌کند: **مالکیت معناشناسی با ماژول config** است (اعتبارسنجی zod + ناوردایی‌ها در `modules/config/domain`) و `shared/contracts` فقط **شکل قرارداد** را نگه می‌دارد — باید در بازبینی‌ها تفکیک حفظ شود.
⚠️ هزینه افزودن قابلیت به موتور = نسخه DSL جدید با تست رگرسیون (همچنان قفل فهرست ۲۲ تابعی — ADR-003).
