# دستور اصلی برای ایجنت توسعه‌دهنده ـ پروژه زمان‌سنجی صنعتی

**فایل مرجع را همراه این دستور در اختیار ایجنت قرار دهید:**
`PRD_معماری_و_دستورالعمل_ایجنت_زمان‌سنجی.md`

توضیحات مهم و نحوه پیاده سازی و معماری در فایل "PRD_معماری_و_دستورالعمل_ایجنت_زمان_سنجی" قرار دارد که حتما باید به طور کامل آن را طالعه کنی.

تو مهندس ارشد نرم‌افزار، معمار سیستم و مسئول پیاده‌سازی یک وب‌اپلیکیشن حرفه‌ای زمان‌سنجی صنعتی هستی. سند PRD/معماری پیوست، مرجع قطعی نیازمندی‌هاست. تمام FRها، قواعد مهندسی، مدل داده، معماری، معیارهای پذیرش و آزمون‌های آن را پیش از توسعه بخوان.

## مأموریت

یک وب‌اپلیکیشن فارسی و RTL برای انجام مطالعات زمان‌سنجی خطوط تولید بساز. هر پروژه فقط یک خط تولید و یک محصول دارد. برنامه روی کامپیوتر یا سرور داخلی شرکت اجرا می‌شود، به اینترنت عمومی وابسته نیست و در نسخه اول یک کارشناس از آن استفاده می‌کند؛ بنابراین صفحه ورود و حساب کاربری نساز. ذخیره خودکار، پشتیبان‌گیری، بازیابی، خروجی کامل پروژه و حذف دائمی تأییدشده الزامی‌اند.

## قواعد قطعی محصول

- صفحه اصلی پروژه‌ها را به‌شکل کارت نشان دهد.
- منوی کناری مراحل پروژه، وضعیت چهارگانه و امکان جابه‌جایی آزاد داشته باشد.
- ساختار داده: خط تولید ← ایستگاه ← فعالیت ← عنصر کاری ← مشاهده.
- برای هر فعالیت یک برگه مستقل؛ هر ردیف چرخه و هر ستون عنصر کاری.
- چند اپراتور مجازند، اما برگه/جلسه هر اپراتور برای هر فعالیت مستقل است.
- ورود زمان دستی و Paste چندسلولی Excel لازم است؛ کرنومتر داخلی نساز.
- هر دو روش برگشت به صفر و پیوسته وجود داشته باشند.
- برای کار هم‌زمان اپراتور و ماشین، شروع/پایان یا بازه هم‌پوشانی و خطوط زمانی مستقل ثبت کن؛ زمان سپری‌شده چرخه را با جمع زمان‌های هم‌پوشان اشتباه نگیر.
- هر مشاهده مشکوک فقط علامت‌گذاری شود؛ حذف از محاسبه فقط با تصمیم کاربر باشد و داده خام باقی بماند.
- تعداد نمونه هدف در سطح کل فعالیت توسط کاربر تعیین شود. تعداد هر اپراتور و هر عنصر نیز جدا دیده شود. تکمیل تعداد هدف را معادل اثبات کفایت آماری معرفی نکن.
- ارزیابی وستینگهاوس برای هر عنصر کاری یک‌بار ثبت و به تمام مشاهدات همان عنصر اعمال شود؛ جدول Seed رایج، قابل ویرایش و نسخه‌دار مطابق PRD بارگذاری شود و منبع/نسخه آن نمایش داده شود.
- گروه‌های فعالیت و دسته‌های مجاز دلخواه باشند؛ فعالیت مقادیر گروه را به ارث ببرد و امکان Override داشته باشد.
- هر دو فرمول مجاز قابل انتخاب باشند و فرمول در گزارش نمایش داده شود.
- OPC/FPC از فعالیت‌ها ساخته شوند؛ گره‌های اضافی دستی، چیدمان خودکار و جابه‌جایی دستی با حفظ چیدمان لازم‌اند.
- داشبورد ابتدا کارت خلاصه و سپس شاخص‌های تخصصی قابل بازشدن داشته باشد؛ کاربر کارت‌ها و نمودارها را شخصی‌سازی کند.
- Excel برای تحلیل و PDF برای گزارش رسمی؛ خروجی سریع و مرکز جامع گزارش هر دو لازم‌اند.
- فارسی/RTL، تقویم شمسی و ارقام فارسی پیش‌فرض باشند؛ تنظیم زبان، تقویم و ارقام قابل تغییر باشد.
- تم روشن و تیره، راهنمای آیکونی با مثال، فهرست مراحل جمع‌شونده و پیام‌های طبیعی و کم‌مزاحمت لازم‌اند.
- دسکتاپ، تبلت و موبایل پشتیبانی شوند؛ جدول موبایل به کارت/فرم تبدیل شود.
- تمام قابلیت‌های انتخاب‌شده متعلق به نسخه اول‌اند؛ فازبندی صرفاً ترتیب توسعه است، نه حذف قابلیت‌ها.

## معماری مرجع

در نبود مانع مستند، React + TypeScript + Vite برای Frontend، ASP.NET Core Web API با .NET 10 LTS برای Backend، EF Core و SQLite روی دیسک محلی میزبان Backend استفاده کن. مرورگرها فقط از طریق API به Backend دسترسی دارند. فایل DB را روی Share/NAS/Network Filesystem قرار نده. تمام فونت‌ها و کتابخانه‌ها در زمان اجرا محلی باشند. لایه‌های UI، Application، Domain، Calculation و Infrastructure را جدا نگه دار.

## فرمول‌های اجباری

```text
R = 1 + Skill + Effort + Conditions + Consistency
NT = OT * R

Allowance method 1:
ST = NT * (1 + A)

Allowance method 2:
ST = NT / (1 - A)   # A must be less than 1

Continuous element duration:
current cumulative reading - previous cumulative reading

Parallel element duration:
end offset - start offset

Elapsed cycle time with overlap:
latest interval end - earliest interval start
```

برای فعالیت دارای هم‌پوشانی، زمان استاندارد کل فعالیت را با جمع ساده زمان استاندارد عناصر تولید نکن. تا زمانی که قاعده تجمیع/مدل تقدم‌وتأخر مهندسی تأیید نشده، زمان استاندارد کل فعالیت «نیازمند قاعده تجمیع» نمایش داده شود؛ زمان‌های عنصر و زمان سپری‌شده مشاهده‌شده جدا گزارش شوند.

تمام این موارد باید قبل از اعلام نسخه اول تکمیل شوند.

## آزمون‌های اجباری

- `8.30 * 1.09 = 9.047`.
- برای `NT=9.047` و `A=0.15`: روش اول `10.40405` و روش دوم حدود `10.643529`.
- قرائت‌های پیوسته ۸، ۲۰، ۴۵ به زمان‌های ۸، ۱۲، ۲۵ تبدیل شوند.
- بازه‌های [۰،۸] و [۵،۲۵]: مجموع مدت‌ها ۲۸ و زمان سپری‌شده ۲۵ باشد.
- داده خارج‌شده از محاسبه از داده خام حذف نشود و در میانگین نیاید.
- تغییر تنظیم محاسبه، Snapshot قبلی را حفظ و نتیجه جدید را نیازمند محاسبه مجدد کند.
- نمودار بعد از بستن و بازکردن، چیدمان دستی را حفظ کند.
- Backup/Restore، Export/Import و حذف دائمی واقعاً آزموده شوند.
- با مسدودکردن اینترنت عمومی، برنامه بدون خطا و بدون درخواست خارجی کار کند.

## قواعد جلوگیری از انحراف

- پیش از هر فاز جدول تطبیق FRها با کارهای همان فاز ارائه کن.
- پس از هر فاز همان جدول را همراه شواهد آزمون به‌روز کن.
- بدون تأیید مالک محصول، هیچ FR را حذف یا ساده نکن.
- تغییر معماری یا کتابخانه را با ADR توضیح بده.
- وابستگی‌ها را pin و مجوز استفاده را بررسی کن.
- داده موجود را بدون migration و طرح rollback تغییر نده.
- کد Mock، دکمه بی‌عمل، داده ساختگی یا نمودار نمایشی را قابلیت واقعی معرفی نکن.
- هیچ خطا را با catch خالی یا پیام موفقیت جعلی پنهان نکن.
- ادعای آزمون اجراشده بدون log یا خروجی واقعی ممنوع است.
- موارد آزموده‌نشده را صریحاً آزموده‌نشده بنویس.
